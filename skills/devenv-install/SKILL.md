# 开发环境安装（devenv-install）

从**官网**取证、逐个安装开发工具链（Go / Rust / Node·npm·pnpm / Zig / Bun / Beads 等）。**仅显式调用激活**（`/devenv-install` 或点名 devenv-install + 工具名），不因「装个环境」「配下依赖」等字样自动触发。

入参是工具清单：`devenv-install go rust node/pnpm`。缺入参 → 只问要装什么，不猜。**用户输入了几个工具，就给几次审阅**——每个工具独立一轮，绝不打包审批。

## 铁律

- **只认官网**：版本号、下载地址、安装命令、校验和一律取自该工具官网（预设文件里列出的官方域名）。第三方博客、镜像站的版本信息只作参考，不作为事实来源；镜像只允许用在「下载」这一步，事实仍以官网为准。
- **逐个审阅**：每个工具独立走「检测 → 摘要 → 命令 → 用户批准 → 执行 → 验证」，检测到已装时多一道用户决策门。未获明确同意不执行任何写操作。
- **先读预设**：处理某工具前先读 `presets/<工具>.md`——里面沉淀了该工具的官网入口、检测/安装/验证命令、镜像与坑，是本 skill 的事实底座。预设头部标有**上次核对日期**：日期越旧越要谨慎；处理中发现预设与官网不符（命令 / URL / 命名变了）→ 装完后把修正写回预设并刷新日期，写回前跟用户说一声。
- **无预设先问**：预设外的工具不自行搜索就装——搜索结果可能撞上 SEO 污染与仿冒站。先向用户说明安全风险，按 §3 三选一（用户指引方向 / 系统自带包管理 / 放弃本次），用户不选就不动。

## 0. 摸清现场

```bash
uname -m                              # x86_64 / aarch64，选对架构
head -5 /etc/os-release 2>/dev/null   # 发行版，决定包管理器；macOS 则跳过
echo $SHELL                           # 改 PATH 时写对 rc 文件
```

入参归一：`golang` → go；`node` / `npm` / `pnpm` → nodejs 组（同一生态，共用一份预设）。去重后按用户给的顺序处理。预设没覆盖的工具走 §3 兜底流程，不现场瞎编安装命令。

## 1. 逐个安装（每工具一轮，串行）

对清单里每个工具依次执行；一轮走完才进下一轮，某个失败不堵死后面的。

1. **读预设**：nodejs 组一个文件覆盖 node / npm / pnpm 三个名字。
2. **已装检测（必做，第一步就做）**：跑预设的检测命令——有没有、什么版本、装在哪。`which -a` 可查出多份并存；被版本管理器（nvm / fnm / rustup / brew 等）管的要认出来，标注「由谁管理」。
3. **官网取证**：用预设给出的官网页面抓**当前最新稳定版**、适用的安装方式与校验和——已装时用于对照，未装时用于生成方案。抓取失败重试一次；仍失败 → 如实告知，用户可选稍后再试，或按预设的通用安装法继续（明确标注「版本未经官网实时核实」）。
4. **已有 → 用户决策门（必做）**：只要检测到已存在——哪怕与官网同版本——就停下，让用户自己决策，模型不代选：

   ```text
   ▶ Node.js：本机已有 v20.11.0（nvm 管理），官网最新 LTS v24.20.0
     1) 跳过，保持现状
     2) 沿用 nvm 升级到最新 LTS（推荐：现有版本由它管，不并行装第二份）
     3) 卸载现有的，换官方 tarball 重装
   ```

   选项按现场生成，通常三类：跳过 / 沿用现有方式升级 / 重装或换方式。模型可以给推荐与理由（如「版本管理器管的不建议并行再装一份」），但**选哪个由用户定**。选跳过 → 记录结果，进下一个工具；选升级或重装 → 按所选路径进第 5 步。
5. **摘要**（审阅门第一半）：

   ```text
   ▶ Go（第 1/2 个）
     信息来源：https://go.dev/dl（官网）
     最新稳定版：go1.27.1（下载页含官方 SHA256）
     本机：未安装 / 已装 go1.21.x（落后 2 个大版本）
     计划：Linux x86_64 官方 tarball → /usr/local/go，PATH 写入 ~/.zshrc
   ```

6. **命令 + 审阅门（必做）**：给出按预设与用户所选路径生成的安装命令，等用户明确同意。用户改了命令就按改的执行；预设里有多条路线（如 node 的 tarball / NodeSource / 版本管理器）→ 摘要里写明推荐与理由，让用户挑。
7. **执行与验证**：执行 → 跑预设的验证命令确认版本 → 新 shell 语义下确认 PATH 生效（如 `zsh -ic 'go version'`）→ 记录结果，进下一轮。

npm 这类「随宿主一起就位」的工具：node 装好 npm 即可用，不单独生成安装命令，但摘要里单独一行说明去向，仍算独立一次审阅确认。

## 2. 下载不通 → 中国大陆镜像

官方源下载失败（超时 / 连接重置 / 速度趋近 0）时停下：

1. **问用户：「下载不通，你在中国大陆吗？」** —— 不自行切镜像。
2. 在大陆 → 列出预设「中国大陆镜像」一节的可选项（各自由谁维护、什么性质），**让用户挑一个**；预设没收录就现场搜，说明来源与风险后再让用户定。
3. 用选中的镜像重试下载；**校验和仍用官网公布的值核对**，镜像没有校验和就明示风险由用户定夺。
4. 不在大陆 → 报告失败原因，问重试还是跳过该工具。

镜像尽量只作用在「下载」这一步，不改安装脚本：Go 换下载域名；rustup 用 `RUSTUP_DIST_SERVER` 等环境变量；node 换 dist 镜像 URL 或版本管理器的 mirror 变量。

## 3. 没有预设的工具（先过安全决策门）

预设没覆盖的工具，模型手上没有核实过的官网与安装事实；自行搜索容易撞上 SEO 污染与仿冒站（typosquat 域名、假文档站），风险高于有预设的工具。因此**先停下，向用户说明风险并让用户三选一**，用户不选就不动：

1. **用户指引方向**：请用户给出官方网站 / 安装来源（口头说个地址即可）。按用户给的来源核实后，回到 §1 主流程（摘要、审阅门、验证一个不少）。
2. **系统自带包管理安装**：用当前系统的原生包管理器（apt / dnf / pacman / brew 等）。来源是发行版仓库，供应链相对可信；摘要里注明「版本通常滞后于官方最新」。不擅自添加第三方仓库 / PPA / AUR——那等于引入未核实来源，用户点名要才加并标注风险。
3. **放弃本次执行**：记录「未安装（无预设，用户选择放弃）」，进下一个工具，总结里如实标注。

选 1 或 2 装完后建议沉淀：按现有预设的章节结构（**头部核对日期**、官网与权威来源、已装检测、安装方式、验证、中国大陆镜像、坑）写 `presets/<工具>.md`，注明本次实际走的是哪条来源，经用户确认后落盘，下次直接走主流程。

## 4. 总结

全部轮次跑完给结果表：

```text
devenv-install 完成：2 装 / 1 跳过 / 0 失败
- go     go1.27.1        ✅ 已装并验证（官网 tarball，来源 go.dev/dl）
- rust   <最新稳定版>     ✅ 已装并验证（rustup，下载走 rsproxy.cn）
- pnpm   —               ⏭️ 用户选择跳过（已有 npm 全局安装）
提醒：PATH 改动需重开终端或 source 一次生效；GOPROXY / npm registry 等日常源未动，需要可再配置。
```
