# ADR 格式

ADR 存放在 `docs/adr/`，按顺序编号：`0001-slug.md`、`0002-slug.md`……

`docs/adr/` 目录惰性创建：第一份 ADR 需要时再建。

## 模板

```md
# {决策的一句话标题}

{1–3 句话：什么背景、决定了什么、为什么。}
```

就这样。一份 ADR 可以只有一段话。价值在于记录**做过决策及其原因**，而不是填满小节。

## 可选小节

只在确有增量价值时加，多数 ADR 用不上：

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策会被重新审视时才有用
- **Considered Options**：被否的方案值得记住时才写
- **Consequences**：下游影响不明显、需要点明时才写

## 编号

扫 `docs/adr/` 取最大现有编号 +1。

## 何时该写 ADR

三条必须全真：

1. **难以逆转**：事后改主意的代价实打实
2. **缺了上下文会让人费解**：未来的读者看到代码会问「为什么偏偏这么做？」
3. **真实权衡的结果**：确实存在别的选项，你因具体理由选了其一

易逆转的决策不写——到时候直接改就行；不令人意外的不写——没人会问为什么；没有真实备选项的不写——除了「我们做了显而易见的事」没别的可记。

### 什么够格

- **架构形态**：「用 monorepo」「写模型事件溯源，读模型投影进 Postgres」。
- **context 之间的集成方式**：「Ordering 与 Billing 走领域事件通信，不同步 HTTP」。
- **带锁定的技术选型**：数据库、消息总线、认证服务、部署目标。不是每个库都算——只算换掉要一个季度的那些。
- **边界与归属**：「Customer 数据归 Customer context 所有，其他 context 只引用 ID」。明确的「不做」和「做」一样值钱。
- **刻意偏离惯常路线**：「不用 ORM、手写 SQL，因为 X」。理性读者会默认相反做法的一切——这类记录能阻止下一个人把刻意为之的事「修好」。
- **代码里看不见的约束**：「因合规要求不能用 AWS」「因合作方 API 契约，响应必须 <200ms」。
- **否决理由不明显的备选项**：考虑过 GraphQL 但因微妙理由选了 REST，就记下来；否则半年后还会有人提议 GraphQL。
